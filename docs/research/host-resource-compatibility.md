# V1 host/resource compatibility research

**Purpose:** Ground Agent Depot's V1 host/category matrix in each host's current official documentation. This is a compatibility survey, not a promise that every host version or operating system supports every installation method. The sources below document host behavior; they do not establish Agent Depot's minimum supported host versions.

## Cross-host conclusions

1. **Skills are the only strong shared resource shape.** All four hosts document `SKILL.md`-based skills, but their discovery paths differ. Pi, Codex, and OpenCode document the shared `.agents/skills` convention; Claude Code documents `.claude/skills` and does not document `.agents/skills` as a direct discovery location. Agent Depot can use `.agents/skills` as the canonical project path and `~/.agents/skills` as the canonical user-global path, then create a user-selected symlink entry under Claude Code's documented location. Claude's skills documentation documents support for symlinked skill directories, so Claude can consume the shared source without a duplicate content copy. This intentionally may expose a Claude-only selection to Pi, Codex, or OpenCode through their shared discovery convention. The file format has common ground, but host-specific metadata and behavior should not be assumed portable.
2. **Agent definitions are host-native formats, not one portable format.** Claude and OpenCode use Markdown with frontmatter, Codex uses TOML, and Pi has no standalone native definition documented. Do not convert one host's agent definition into another host's format automatically.
3. **“Plugin/extension” is a category, not a common package format.** Pi packages, Claude plugins, Codex plugins, and OpenCode plugins have different manifests, loading mechanisms, and executable-code behavior. Discover and install only a recognized host-native package; do not treat an arbitrary plugin directory as compatible with every selected host.
4. **MCP is a shared protocol, but host configuration is not shared.** Claude JSON, Codex TOML, and OpenCode JSON/JSONC configurations differ. Pi needs an explicitly installed MCP adapter. A portable MCP resource must be translated only through a known host adapter; Agent Depot should not guess from a server name or arbitrary config file.
5. **CLI applications are not host-specific.** Compatibility should be evaluated against OS, architecture, and runtime/package-manager requirements. They should not be filtered by the selected coding-agent host set.
6. **Linux/Windows compatibility still needs per-adapter validation.** Host documentation uses different home-relative/project-relative locations. For example, Claude documents `%USERPROFILE%\\.claude` on native Windows, OpenCode documents `%USERPROFILE%\\.config\\opencode` and recommends WSL for the best Windows experience, and Codex/Pi document home-relative paths. Resolve paths through the current user's home and each host's documented config rules; do not infer that a working Linux path is valid on Windows. ([Claude directory](https://code.claude.com/docs/en/claude-directory), [OpenCode Windows](https://opencode.ai/docs/windows-wsl), [OpenCode troubleshooting](https://dev.opencode.ai/docs/troubleshooting/), [Pi configuration](https://pi.dev/docs/latest/configuration), [Codex skills](https://developers.openai.com/codex/skills))

## Recommended V1 interpretation

The user-confirmed V1 scope is **portable directory-based skills, user-global Apps, and host-native Packages**. The CLI application, agent-definition, and MCP matrix entries are retained as factual compatibility research, but those categories are deferred and are not V1 commitments.

- Manage **skills** as a confirmed V1 host-targeted resource type, with `.agents/skills` and `~/.agents/skills` as the canonical project and user-global paths for new installations. When Claude Code is selected, create a symlink entry under `.claude/skills` or `~/.claude/skills` pointing to the canonical directory. This follows Claude's documented symlink support without implying that Claude Code natively scans `.agents/skills`; the shared path may still expose a Claude-only selection to Pi, Codex, or OpenCode. The file format has common ground across the four hosts, but host-specific metadata and behavior still require validation.
- Manage **Packages** as a confirmed V1 category by delegating lifecycle to each host's own CLI: Pi packages via `pi install`/`pi update --extensions`/`pi remove` from a repository-root Git Source, and Claude Code plugins via `claude plugin marketplace add` then `claude plugin install <plugin>@<marketplace>` from a marketplace bound inside the same repository. Discover and install only a recognized host-native package; do not treat an arbitrary plugin directory as compatible with every selected host, and never treat a bundle's skills as a second managed copy. Installed state is read from the host's own files, so `unknown` is a first-class status.
- **CLI applications**, **agent definitions**, and **MCP servers** are deferred and not committed to V1 as independent categories. Their matrix entries document possible future compatibility work; they do not authorize V1 discovery, installation, or adapter requirements. A Package that carries agent definitions or MCP servers reports them as `host-only` components and leaves them to the host. If a future scope decision includes them, compatibility must be based on recognized host-native formats and explicit adapters rather than category names alone.
- Preserve the approved safety behavior for V1 skills: unrecognized resources remain visible for manual identification, but are not silently assigned a target or installed; incompatible skills remain visible with a reason and are excluded from `all`.
- Record supported V1 skill/host combinations explicitly before implementation. The current host docs do not establish Agent Depot's minimum host versions, so those versions remain an implementation prerequisite.
- If an installed skill is already present, adopt it in place without reinstalling when its content exactly matches the selected source, including when it is at a noncanonical location, and track its actual location. Do not move it or create an additional host-location link or copy without explicit confirmation if later host expansion needs another location. A same-name, different-content skill is a conflict and must not be overwritten without explicit confirmation; the exact comparison and conflict-resolution details remain open.
- **Windows symlink constraints:** Claude Code documents symlinked skill folders. Node.js `fs.symlink` supports `dir`, `file`, and `junction` link types on Windows; a junction is directory-only and requires an absolute target. Node's current bundled libuv source passes `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE` when creating a normal Windows symbolic link, and retries without that flag only when Windows reports `ERROR_INVALID_PARAMETER` (unsupported flag). It does not silently fall back to copying when link creation is denied. Microsoft says the ordinary symbolic-link creation right defaults to Administrators; the API flag is intended to allow non-elevated creation, with a Developer Mode caveat documented for UWP. Therefore creation can work without elevation on supported configurations, but permission/OS-policy failures must still be handled. A junction is a possible alternative, not yet proven to be treated as the documented symlink by Claude Code. The fallback policy is resolved: if symlink creation fails, including on Windows, stop the target operation with actionable guidance and do not create a duplicate managed copy. Testing symlink creation on a standard non-admin Windows account and confirming Claude discovery remain future validation work. ([Claude skills and symlinks](https://code.claude.com/docs/en/skills), [Node.js fs.symlink](https://nodejs.org/api/fs.html#fspromisessymlinktarget-path-type), [Node/libuv Windows symlink implementation](https://github.com/nodejs/node/blob/main/deps/uv/src/win/fs.c), [Windows symbolic-link privilege](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/create-symbolic-links), [CreateSymbolicLink API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinka), [Windows mklink](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/mklink))

## Source notes

All links above are first-party host documentation or the official Pi package listing. The Codex plugin page is OpenAI's official packaging guide. The Claude skills documentation is also the source for the documented symlink support used by the shared-path mapping; it does not document `.agents/skills` as a Claude discovery location. The statement about Pi MCP is intentionally scoped to the reviewed core documentation: the docs review found a separate adapter package, not a claim that no third-party or future Pi integration can exist. OpenCode recommends WSL on Windows for the best experience, while also stating that OpenCode can run directly on Windows.
